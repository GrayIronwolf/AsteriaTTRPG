# Firebase / Firestore audit and remediation

Repository: `GrayIronwolf/AsteriaTTRPG`. Baseline: `81256779d6d44b32f477239d0f7528f046666f3e`. Audit date: 2026-09-09. This report distinguishes repository findings from production state. Firebase Console, deployed rules, billing, usage, IAM and real user records were not available to this workspace. No production data was changed.

## Original architecture

The static website loads a legacy application plus React dashboard bundles from `react-dist`. `js/firebase-auth.js` owns a modular Firebase browser SDK instance for project `asteria-ttrpg`, Firebase Authentication (email/password, persistent browser sessions), Firestore and Storage. The React service is an adapter over `window.AsteriaFirebase`, not a second Firebase initialization. `src/dev-entry.js` selects the React bundle or Vite entry. Local fixture mode replaces the API only when explicitly requested.

Firestore has private account documents under `users/{uid}` with characters, campaigns and settings. Shared campaign documents contain membership and character links; subcollections contain characters, current/live session data, historical sessions/presence, events and party chat. `systems` contains GM workspace, encounter, party workspace, item ecosystem and a legacy progression mirror. `customItems` is a shared authenticated catalog. `campaignInvites` maps invitation codes. The old `usernames` directory stored account emails. Storage holds character gallery objects under owner paths.

The data path was: React UI → local React state/action → service adapter → browser Firestore transaction → campaign documents/events → `onSnapshot` listeners → React state → UI. A second legacy path in `js/data-sync.js` discovered campaigns, merged snapshots into global state, persisted private copies and wrapped global saves. Thus incoming data could trigger another outgoing save. Local copies and shared campaign state could diverge when errors were swallowed.

Configuration originally lived in `js/firebase-auth.js`, `firebase.json`, `.firebaserc`, `firestore.rules`, `firestore.indexes.json` and `storage.rules`. The index file was empty. There was no `.gitignore`, environment template, emulator setup or GitHub deployment/check workflow. Ordinary local development used the production project.

## Findings: problem → cause → impact → fix

## Rules, indexes and security evidence

There was no demonstrated missing composite index in the baseline queries: those inspected used simple filters. The new bounded owner event query needs an owner/creation-time composite index, supplied alongside the owner/acknowledgement index. Production readiness must be verified in the Console; emulators do not enforce production composite-index requirements.

The prior history scan covered the fetched main history (55 commits, 2,079 text objects) and found no matching private-key/service-account/token patterns. The current changes add no private credentials. This is pattern-based evidence, not a guarantee that every possible secret format was absent. The committed Firebase **web** API key is public client configuration, not an Admin private key; its presence alone does not require rotation. No actual secret was identified that could responsibly be declared revoked or rotated.

`.gitignore` now excludes environment files, common service-account/Admin/ADC and CI credential filenames, keys, emulator exports and logs. The Functions packaging ignore list also excludes these files. GitHub secret scanning and review remain necessary for arbitrary filenames.

## Architecture after the change

The browser still has one Firebase owner and one React adapter. Canonical player writes are in `functions/commands.mjs`, reached through `functions/handler.mjs` and the authenticated `asteriaAction` callable. The server checks membership and ownership inside the same transaction as reads/writes and stores a request receipt to prevent duplicate execution of the same request ID. Talent metadata and stored/compendium spell costs are checked on the server. GM transactions continue to use scoped Firestore rules. Invitations use the separate authenticated `asteriaInvite` callable.

Legacy account discovery and private mirrors remain for compatibility. They are no longer allowed to override protected shared gameplay state. The old progression service and fixture implementation are still present, but the active React gameplay path uses the shared characters/events and server commands. Fixtures are testing aids, not a second production database. Generated bundles are rebuilt and obsolete generated chunks removed.

Recommended structure is now implemented: root Firebase CLI/rules/index/environment template, `functions/` server code, `src/firebase/` adapter, `src/sessions/` listeners, shared state models, `scripts/` behavioral tests, `docs/` audit, and `.github/workflows/` checks/manual deployment. See `FIREBASE-SETUP.md` for secure Codex use, Workload Identity Federation, files/secrets placement and the deployment order.

## Validation and limits

The existing armour, pricing, React, stability and smoke suites pass (553 checks); the separate live XP/loot regression passes. Five added sync regression tests cover feedback prevention, failed saves, queued saves, retries and logout. Firebase integration tests cover real rules, cross-account authorization, atomic resource delivery, request deduplication, saved spell costs, item exchange, gallery access, invitation joining, initial character linking, reward replay, local HTTP callable Auth and shop stock. The production React bundle builds successfully.

The full Functions emulator could load definitions but its Unix socket listener was denied in this workspace. The real exported callable was therefore tested over local HTTP with Auth/Firestore emulators instead. Node 24 was available locally; CI and deployment are configured for Node 22. Production billing, authorized domains, IAM, deployed rules/indexes, real multi-device behavior and quota usage remain unverified.

The screenshot's “Quota exceeded” cannot be conclusively attributed to a specific quota from repository code alone. The feedback loop and frequent writes plausibly contributed; `resource-exhausted`, `permission-denied`, missing-index errors and browser storage exhaustion require different remedies. Inspect the actual error code and Firebase Usage before changing billing. A missing scratch image file is a separate attachment-path problem.
